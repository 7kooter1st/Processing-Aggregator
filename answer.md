Ниже приведено подробное общее объяснение архитектуры, потоков данных и логики работы каждого сервиса.

---

## Общая архитектура системы (The Pipeline)

Ваша система будет состоять из четырех основных компонентов/этапов:

1. **Input Service (Ingestor):** получает PDF/DOCX.
2. **Chunking & Producer:** преобразует данные в мелкие, последовательные сообщения и отправляет их в Kafka.
3. **Processing Service (Consumer → Ollama Orchestrator):** читает из Kafka, управляет взаимодействием с локальной LLM (Ollama), обрабатывает каждый кусок текста и сохраняет промежуточный результат.
4. **Output/Aggregator:** считывает готовые или промежуточные результаты и отправляет их обратно на фронтенд.

### Необходимые Kafka Topics (темы)

Для корректной работы вам потребуется минимум три темы:

1. `**raw_chunks`** — куски сырого текста, полученные из документа, ожидающие анализа.
2. `**processed_results**` — промежуточные или финальные результаты обработки от Ollama.
3. `**status_updates**` — сигнализирует фронтенду о статусе выполнения («Обработка шага 5/10 завершена»).

---

## Этап 1: Подготовка и парсинг (The Ingestor → Chunking)

Этот этап происходит на вашем первом сервисе. Его задача — преобразовать сложный формат в простой поток данных для Kafka.

**Действия:**

1. **Загрузка:** принимает PDF/DOCX от фронтенда.
2. **Извлечение (OCR & Extraction):** если это PDF с изображениями, используется OCR (Tesseract, Google Vision API и т.д.) для преобразования изображений в текст. Все данные преобразуются в единый текстовый поток.
3. **Разделение на куски (Chunking):** самый важный шаг. Вы разбиваете большой поток текста не по фиксированному количеству символов, а так, чтобы каждый кусок был логически завершён и соответствовал лимиту LLM (≈ 1000–2000 токенов).
4. **Формирование сообщения:** каждое сообщение в Kafka должно содержать не только чанк текста (`content`), но и критически важные метаданные:
  - `document_id` — уникальный ID документа (для отслеживания прогресса);
  - `chunk_index` — номер куска в документе (например, 1 из 50);
  - `total_chunks` — общее количество кусков.

**Результат:** множество сообщений попадает в топик `**raw_chunks`**.

---

## Этап 2: Обработка и оркестрация (The Consumer → Ollama)

Это сердце системы. Ваш сервис-потребитель (`Consumer`) должен быть умнее, чем просто читатель; он должен быть **оркестратором**.

### Логика работы сервиса-консьюмера

1. **Подписка:** сервис подписывается на топик `raw_chunks`.
2. **Получение задачи:** получает сообщение (Chunk N, Document ID X).
3. **Контекстное построение Prompt:** он не просто отправляет текст куска в Ollama. Он должен собрать *цельный, направленный промпт* для данной итерации:
  > «Ты — эксперт по сравнению документов. Твоя текущая задача — сравнить данные из "Документ А" и "Документ Б" только в том разделе, который описывает [Тема]. Ниже представлен Кусок N текста из Документа А и Кусок N текста из Документа Б. Найди все расхождения по заданной теме и верни ответ строго в формате JSON.»
4. **Вызов Ollama:** отправляет этот скомбинированный промпт на локальную модель через API Ollama.
5. **Получение результата:** получает частичный, структурированный результат (например, найденные расхождения для данного раздела).
6. **Сохранение/передача:** этот результат должен быть отправлен в топик `**processed_results`**.

### Управление состоянием (State Management)

Это самый сложный момент: вам нужно знать, что вся задача по документу X завершена, прежде чем вы сможете отправить финальный ответ.

**Решение:** сервис должен вести учёт в базе данных или кеше (Redis).

- При получении `document_id` и `total_chunks` он записывает: «Документ X ожидается результат с кусков 1 до N».
- По мере получения каждого результата он обновляет счётчик. Когда получен последний результат (`chunk_index == total_chunks`), процесс считается завершённым.

---

## Этап 3: Сборка и отправка результатов (The Aggregator)

Отдельный сервис или функция должна слушать топик `processed_results`.

**Действия:**

1. **Сбор:** слушает все результаты, поступающие по конкретному `document_id`.
2. **Агрегация:** собирает эти частичные результаты в одну конечную структуру данных (например, один большой JSON-объект).
3. **Финализация и отправка:** как только сервис-потребитель завершил обработку всех кусков для этого документа (проверил по своему внутреннему счётчику):
  - отправляет сигнал в топик `status_updates` («Document X: Готово! Результат готов.»);
  - передаёт финальный агрегированный результат на фронтенд (через WebSockets, подключённый к этому статусу).

## Итоговый поток данных (Summary Flow)


| Шаг   | Источник → Назначение                                 | Компонент              | Действие                                                                          |
| ----- | ----------------------------------------------------- | ---------------------- | --------------------------------------------------------------------------------- |
| **0** | Фронтенд → Ingestor                                   | Парсинг PDF/OCR        | Преобразование в сырой текст.                                                     |
| **1** | Parser → Kafka Topic: `raw_chunks`                    | Chunking Logic         | Разделение текста на логические куски, добавление метаданных (`doc_id`, `index`). |
| **2** | Consumer (Raw) → Ollama API                           | Orchestrator Service   | Читает кусок. Формирует промпт для сравнения/анализа. Отправляет запрос.          |
| **3** | Ollama API → Consumer (Process)                       | Local LLM              | Возвращает частичный результат, структурированный JSON-фрагмент.                  |
| **4** | Consumer (Process) → Kafka Topic: `processed_results` | Producer Logic         | Сохраняет промежуточный результат и обновляет счётчик прогресса для `doc_id`.     |
| **5** | Aggregator Service (Status Listeners)                 | Сборка/финальный вывод | Когда получен последний кусок, собирает все части вместе в финальный ответ.       |
| **6** | Aggregator → WebSockets → Фронтенд                    | Клиентская логика      | Отправляет конечное сообщение: «Обработка завершена! Вот результаты.»             |

## Рекомендации по реализации

1. **Транзакционность:** используйте `document_id` как ключ сообщения в Kafka. Это гарантирует, что все связанные куски для одного документа обрабатываются потребителями максимально последовательно (при условии, что ваш consumer настроен на обработку ключа).
2. **Идемпотентность:** убедитесь, что если какой-то шаг повторяется (например, из-за сбоя), он не испортит данные. Результаты должны быть *добавляемы*, а не перезаписываемы полностью.
3. **Ошибочная обработка:** реализуйте Dead Letter Topic (DLT) для Kafka. Если один кусок текста вызывает ошибку в Ollama или парсинге, этот кусок должен попадать в специальную очередь для ручного анализа, чтобы не остановить весь пайплайн.
4. **Интерфейс:** в идеале используйте WebSockets на фронтенде, который будет слушать статус от топика `status_updates`, предоставляя пользователю ощущение живого, последовательного прогресса (например, «Анализ 1/50: Сравнение финансовых показателей...»).
